# API 狀態與錯誤文案

僅在撰寫、翻譯或審閱 API 文件、狀態標籤、錯誤碼和介面提示時讀取本檔案。

## 基本原則

- 先確認狀態在目前介面中的真實含義，再選擇中文。
- 不把一個英文狀態詞固定對應成唯一中文。
- 保持 HTTP 狀態、業務狀態、任務狀態和介面提示之間的區別。
- 錯誤文案儘量說明問題、影響和恢復方式。
- 不修改狀態碼、列舉值、欄位名和回應原文。

## 常見狀態詞

- `Success`
  - 根據語意使用 `已完成`、`已處理`、`請求成功`
- `Invalid`
  - 使用 `無效`、`格式有誤`、`驗證未通過`
  - 不預設翻譯成 `非法`
- `Available`
  - 使用 `已開通`、`可取得`、`可存取`、`可使用`
- `Unsupported`
  - 使用 `暫不支援`、`不支援該型別`、`目前不支援`
- `Pending`
  - 使用 `待處理`、`處理中`、`待確認`
- `Expired`
  - 使用 `已過期`
- `Missing`
  - 使用 `缺少`、`未提供`
- `Denied`
  - 使用 `被拒絕`、`未通過`
- `Forbidden`
  - 根據語意使用 `無權限存取`、`目前不允許存取`
- `Not Found`
  - 使用 `未找到對應內容`、`未找到對應資料`
- `Accepted`
  - 使用 `已受理`、`已接收，等待處理`
- `Completed`
  - 使用 `已完成`
- `Failed`
  - 使用 `失敗`、`處理失敗`
- `Conflict`
  - 使用 `狀態衝突`、`資源狀態不一致`、`請求與目前狀態衝突`
- `Unauthorized`
  - 根據實際原因使用 `未登入`、`認證未通過`、`缺少認證資訊`
  - 不機械翻譯成 `未授權`
- `Bad Request`
  - 使用 `請求參數有誤`、`請求格式有誤`
- `Timeout`
  - 使用 `請求逾時`、`處理逾時`

## 參數說明

每個參數儘量寫清：

- 型別和格式
- 是否必填
- 單位
- 預設值
- 允許值或範圍
- 預設行為
- 與其他參數的相依或互斥關係

不要用「正常值」「根據情況填寫」「相關資訊」等無法執行的說明。

## 錯誤文案結構

優先按以下順序提供資訊：

1. 發生了什麼
2. 哪個物件受到影響
3. 可能原因
4. 可以執行的恢復操作
5. 仍然失敗時需要提供的診斷資訊

不要把推測寫成確定原因，也不要在沒有依據時承諾恢復時間。
