# 受控中文技術寫作

本模組借鏡 ASD-STE100 的受控語言思路，用於降低中文技術說明中的歧義和執行風險。它不是 ASD-STE100 的中文版本，也不表示輸出符合或通過 ASD-STE100 認證。

ASD-STE100 是面向英文技術文件的標準。英語受控詞典、詞性、時態和句長規則不能直接移植到中文。本模組只採用可遷移的方法，並根據中文句法和技術寫作語境重新表述。

官方資料：

- [ASD-STE100 官方說明](https://www.asd-ste100.org/about_STE.html)
- [ASD-STE100 Issue 9 取得頁面](https://www.asd-ste100.org/STE_downloads.html)
- [ASD-STE100 工具與合規說明](https://www.asd-ste100.org/STEsoftware.html)

## 適用強度

### 完整應用

- 操作手冊
- 安裝和部署步驟
- 疑難排解
- 維運 Runbook
- 安全警告
- 多步驟 API 呼叫流程

### 選擇性應用

- API 概念說明
- 常見問題
- 更新日誌
- 產品能力說明

選擇性應用術語一致、指代明確和事實保真規則，不強制把所有句子改成操作步驟。

### 不機械應用

- 品牌和落地頁文案
- 敘事性文章
- 法律原文和正式引用
- 需要保留作者風格的內容
- 極短的按鈕和導覽標籤

## 核心原則

### 1. 保留事實

- 不新增來源沒有提供的數字、日期、時限、能力、條件或結論。
- 不刪除警告、限制、例外、單位、預設值和失敗處理。
- 不改變可能、建議、計劃、通常等詞表達的確定程度。

### 2. 一個概念使用一個首選術語

- 為關鍵物件、狀態和動作確定首選術語。
- 不為了避免重複而輪換同義詞。
- 首次出現的縮寫給出全稱；後文保持同一寫法。
- 專案專屬名詞和動詞來自目標專案術語表或可靠上下文。
- 同一個詞存在多個含義時，用更具體的詞消除歧義，不做機械替換。

### 3. 一個步驟包含一個主要動作

- 以明確動作開始步驟。
- 寫清動作物件，不只寫「處理」「操作」「執行」。
- 多個動作必須按順序執行時，拆成編號步驟。
- 兩個動作必須同時完成或構成一個不可分操作時，可以保留在同一步。
- 不為追求短句拆散必要的條件、否定和因果關係。

### 4. 條件和風險先於動作

- 讀者執行動作前必須知道的條件放在動作之前。
- 警告放在可能造成風險的步驟之前。
- 條件較多時，單獨列出前置條件。
- 不把關鍵限制放在步驟末尾的括號中。

### 5. 明確執行者、物件和結果

- 可能出現責任或指代歧義時，寫出執行者。
- 明確區分系統自動行為和人工操作。
- 必要時說明預期結果，便於判斷步驟是否成功。
- 不使用無法定位物件的「該」「其」「此」「上述」「相關」。

### 6. 保持邏輯順序

- 描述操作時按實際執行順序排列。
- 疑難排解先給低風險、可逆和證據價值高的檢查。
- 將原因、現象、操作和結果分開，不混在一個長句中。
- 否定範圍必須明確，避免讀者無法判斷禁止的是哪個動作。

## 操作步驟模板

在適用時按以下結構組織：

1. 前置條件
2. 風險或限制
3. 編號操作步驟
4. 每一步的預期結果
5. 失敗時的停止條件和恢復方式

不要補造原文沒有的預期結果或恢復步驟。資料缺失時標記「待確認」。

## 疑難排解模板

1. 說明可觀察到的現象。
2. 說明需要收集的日誌、狀態或錯誤碼。
3. 按證據和風險安排檢查順序。
4. 對每項檢查寫明判斷條件。
5. 只有證據支援時才給出原因。
6. 寫明恢復操作、驗證方式和停止條件。

不要把「可能原因」改寫成「確定原因」。

## 迴歸範例

以下範例用於檢查事實保真、條件順序、動作邊界和過度簡化風險。改寫後不得增加範例原文沒有的資訊。

### 操作手冊

#### 範例 1

改寫前：

`在安裝代理程式之前需要確認伺服器能夠存取更新位址，然後執行安裝命令。`

改寫後：

1. `確認伺服器能夠存取更新位址。`
2. `執行安裝命令。`

檢查點：條件位於動作之前，沒有增加網路位址或命令。

#### 範例 2

改寫前：

`選擇儲存以後系統會寫入設定並重新載入服務。`

改寫後：

`選擇「儲存」。系統隨後寫入設定並重新載入服務。`

檢查點：區分人工動作和系統行為，不把系統行為誤寫成人工步驟。

#### 範例 3

改寫前：

`如果裝置溫度超過允許範圍，不要繼續啟動裝置。`

改寫後：

`如果裝置溫度超過允許範圍，不要啟動裝置。`

檢查點：保留條件和禁止關係，不補充未知溫度值。

### API 文件

#### 範例 4

改寫前：

`呼叫介面前應設定存取權杖，否則請求會返回認證錯誤。`

改寫後：

`呼叫介面前，設定存取權杖。未設定存取權杖時，請求返回認證錯誤。`

檢查點：前置條件和失敗結果分開，未補充狀態碼。

#### 範例 5

改寫前：

`請求成功後介面會返回任務 ID，後續可以使用這個 ID 查詢處理狀態。`

改寫後：

`請求成功後，介面返回任務 ID。使用該任務 ID 查詢處理狀態。`

檢查點：保持物件名稱一致，避免無法定位的「這個 ID」。

#### 範例 6

改寫前：

`請求失敗時最多重試 3 次，每次間隔 5 秒。`

改寫後：

`請求失敗時，最多重試 3 次。每次重試間隔 5 秒。`

檢查點：原有次數和間隔保持不變。

### 疑難排解

#### 範例 7

改寫前：

`頁面無法開啟時可能是網路問題，可以先檢查瀏覽器是否能夠存取其他網站。`

改寫後：

`頁面無法開啟時，先檢查瀏覽器能否存取其他網站。網路異常是可能原因之一。`

檢查點：沒有把可能原因寫成確定原因。

#### 範例 8

改寫前：

`檢視服務日誌並找到最早出現的錯誤，然後記錄錯誤時間和請求 ID。`

改寫後：

1. `檢視服務日誌，找到最早出現的錯誤。`
2. `記錄錯誤時間和請求 ID。`

檢查點：按執行順序拆分動作，沒有增加日誌位置。

#### 範例 9

改寫前：

`排查期間不要刪除日誌檔案，因為後續分析還需要這些檔案。`

改寫後：

`排查期間，不要刪除日誌檔案。後續分析仍然需要這些檔案。`

檢查點：保留禁止動作和原因。

### 產品介紹

#### 範例 10

改寫前：

`平台提供任務建立、狀態查詢和結果下載能力。`

改寫後：

`平台提供任務建立、狀態查詢和結果下載能力。`

檢查點：原文已經清晰，不為追求變化而改寫。

#### 範例 11

改寫前：

`透過一站式能力賦能團隊快速完成資料處理。`

改寫後：

`平台集中提供資料處理功能，協助團隊快速完成資料處理。`

檢查點：刪除空泛的「一站式能力」和「賦能」，但保留原文已有的「快速」主張；不要擅自補充速度指標。

#### 範例 12

改寫前：

`系統通常會在任務完成後傳送通知。`

改寫後：

`系統通常在任務完成後傳送通知。`

檢查點：保留「通常」表達的不確定程度。

## 自動檢查邊界

可以穩定自動檢查：

- 確定錯字
- 明確的術語大小寫
- 機器可讀內容是否被錯誤處理
- 專案詞表中的確定對應

只應提示人工判斷：

- 一個句子是否包含過多動作
- 條件是否應當提前
- 主語是否需要顯式寫出
- 代詞是否有歧義
- 被動表達是否影響理解
- 文本是否過度簡化
- 改寫是否改變事實或確定程度

不要把句長、被動句、代詞或語境詞設定為無條件失敗規則。自動檢查工具只能提供提示，不能證明文本符合 ASD-STE100，也不能代替作者判斷。
