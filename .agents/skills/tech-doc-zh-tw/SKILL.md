# 繁體中文（台灣）技術文件與產品文案規範

<!-- 作者：Fenng（GitHub：@Fenng） -->

## 適用範圍

將本 Skill 用於繁體中文（台灣）技術內容的撰寫、改寫、校對和審閱，包括：

- 文件首頁、產品介紹、解決方案頁和更新日誌
- API 文件、參數說明、錯誤碼和常見問題
- 操作手冊、疑難排解、維運 Runbook 和安全說明
- 介面文案、按鈕、導覽、狀態和提示資訊

不要改寫程式碼字面量、JSON 鍵名、URL、API 路徑、資料庫欄位名、命令、設定項或其他機器可讀識別碼。

## 規則優先順序

發生衝突時，按以下順序處理：

1. 保留事實、邏輯、限制、安全資訊和法律含義。
2. 服從使用者明確要求和目標專案約定。
3. 保持技術術語和機器可讀內容準確。
4. 改善結構、語意、語氣和可掃讀性。
5. 最後處理標點、留白、大小寫等排版細節。

不得為了句子更短、語氣更確定或格式更統一而犧牲更高優先順序的資訊。

## 事實保真

- 不新增原文或可靠上下文沒有提供的日期、數字、時限、SLA、能力、條件、因果關係或結論。
- 不刪除前置條件、適用範圍、例外、風險、安全警告、相容性說明或失敗處理。
- 不把可能、計劃、建議、通常等不確定表達改成確定事實。
- 資訊不足時保留原意，或明確標記「待確認」；不要自行補全。
- 改寫引用、法規、契約、錯誤原文或使用者提供的固定文案時，優先保持原文並將建議單獨列出。

範例：

- `截止 4 月 12 日` -> `截至 4 月 12 日`
- `儘快處理` -> `在約定時限內處理〔具體時限待確認〕`
- 不要憑空補成 `截至 2026 年 4 月 12 日` 或 `30 分鐘內處理`

## 先判斷任務模式

### 撰寫

- 先確定受眾、內容型別、事實來源、發佈管道和篇幅。
- 缺少會改變結論的事實時，先標記缺口，再繼續組織可確認內容。

### 改寫

- 保留事實、邏輯關係、資訊層級、限制和必要例外。
- 預設交付完整改寫稿；重大語意選擇或待確認內容另行說明。

### 校對

- 只處理約定範圍內的錯字、標點、留白、大小寫和術語一致性。
- 未經要求，不改變結構、語氣或事實表達。

### 審閱

- 先列問題，再給建議；按影響程度排序並引用具體原文。
- 未經授權，不直接修改檔案。

## 核心寫作規則

### 語意與語氣

- 準確先於修辭，清晰先於熱鬧。
- 使用克制、直接、可執行的繁體中文。
- 優先說明「是什麼、適用於什麼、需要做什麼、接著看哪裡」。
- 避免問候式開場、宣傳口號、空泛形容和連續堆疊黑話。
- 預設不直接稱呼讀者；必要時使用明確角色，如「開發者」「實作人員」。
- 第二人稱、驚嘆號和品牌語氣屬於風格選擇；專案約定或特定介面語境可以覆蓋預設規則。

### 結構與句子

- 一個段落承載一個主要資訊點。
- 一個句子保持一個清晰的主幹；不要連續堆疊多個條件、動作和例外。
- 列表項保持相同層級、句式和資訊密度。
- 標題反映用途，不只使用抽象名詞。
- 刪除重複資訊，不刪除事實、條件和例外。
- 指代可能不清時，用具體名稱替代「該」「其」「此」「上述」。

### 術語與排版

- 同一概念使用同一首選術語，不因追求變化而替換同義詞。
- 中文正文使用直角引號 `「」`，巢狀引用使用 `『』`；專案、地區或固定引用規範可以覆蓋。
- 在可見正文中，中文與英文、阿拉伯數字和版本號之間加一個半形空格，例如 `使用 API 取得資料`、`等待 3 秒`、`版本 2.0 已發佈`。
- 中文與行內程式碼之間加一個半形空格；連結按顯示文字判斷留白。中文全形標點前後不額外加空格，不修改程式碼、連結目標、官方名稱和使用者指定字面量。
- 中文段落在原始檔中保持一段一行，不為了控制行寬做硬換行；程式碼塊、表格、標題和列表結構保持原樣。
- 術語、產品名和縮寫優先採用專案規範或官方寫法，不機械替換。
- 不直接批次執行排版替換工具；先保護 Markdown、程式碼和機器可讀內容。

詳細規則見 [術語與排版](references/terminology-and-typography.md)。

## 按內容型別處理

### 入口頁和介紹頁

首段優先回答：

- 內容覆蓋什麼
- 適合誰使用
- 從哪裡開始讀

避免標題、正文和行動按鈕重複同一資訊。

### API 文件

- 請求方法、路徑、欄位和值使用程式碼環境保護。
- 參數說明一列一義，並寫清型別、單位、預設值、限制和是否必填。
- 狀態和錯誤文案根據實際語意翻譯，不機械對應單個英文詞。
- 寫明前置條件、成功結果、失敗結果和恢復方式。

詳細規則見 [API 狀態與錯誤文案](references/api-status-copy.md)。

### 介面文案

- 按鈕說明動作和目標，不重複頁面標題。
- 錯誤提示說明發生了什麼、影響是什麼，以及如何恢復。
- 危險操作寫清物件、後果和是否可撤銷。
- 空狀態區分「沒有資料」「尚未建立」「無權限」和「載入失敗」。

### 操作與疑難排解

對操作手冊、疑難排解、維運 Runbook、安全說明和多步驟 API 流程，讀取並應用 [受控中文技術寫作](references/controlled-technical-chinese.md)。不要把這些規則機械應用於品牌文案、敘事文本或固定引用。

## 專案覆蓋規則

先檢查目標專案自己的 `AGENTS.md`、術語表、品牌規範、既有文件和使用者指示。不要把本 Skill 版本庫中的範例約定當成目標專案約定。

需要建立專案覆蓋檔案時，參考 [專案覆蓋模板](references/project-overrides-example.md)，並將實際檔案放在目標專案中。

## 編輯流程

以下流程按任務模式選擇執行；校對只執行約定範圍內的檢查和修改。

1. 確認任務模式、內容型別、受眾和專案約定。
2. 標記事實、數字、限制、引用和機器可讀內容，建立不可改動邊界。
3. 修復語意錯誤、歧義、遺漏和不一致。
4. 調整資訊順序、段落、標題和列表。
5. 處理語氣、術語、標點、留白和大小寫。
6. 對照原文複核事實、條件、否定範圍、因果關係和確定程度。
7. 執行適用的輕量檢查工具，並人工判斷警告和風格提示。

## 最終檢查

- 是否新增了來源不明的日期、數字、時限、能力或結論
- 是否遺漏了條件、例外、風險、單位、預設值或恢復方式
- 主語、物件、否定範圍、因果關係和確定程度是否保持準確
- 同一概念是否使用同一術語
- 標題、正文、卡片和按鈕是否重複
- 程式碼、路徑、欄位、命令和引用是否保持原樣
- 內容是否便於目標讀者掃讀和執行
- 段落是否殘留硬換行，拼接邊界的中西文留白是否正確
- 專案覆蓋規則是否來自目標專案，而不是範例檔案
